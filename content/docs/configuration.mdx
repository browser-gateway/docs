browser-gateway is configured via a `gateway.yml` file, environment variables, or both.

## Config File Location

The gateway looks for configuration in this order:

1. `--config <path>` CLI flag
2. `BG_CONFIG_PATH` environment variable
3. `$BG_DATA_DIR/gateway.yml` (default writable location, `/data` in Docker, `~/.browser-gateway` outside)
4. `./gateway.yml` in the current directory (legacy)
5. `./gateway.yaml` in the current directory (legacy)

If no file is found on first boot, the gateway seeds `$BG_DATA_DIR/gateway.yml` with a minimal default (`version: 1` + empty `providers`). The dashboard's config editor reads and writes the same path.

## Full Config Reference

```yaml
version: 1

gateway:
  port: 9500                          # Server port (default: 9500)
  defaultStrategy: priority-chain      # How the gateway chooses which provider to use
                                       # Options: priority-chain, round-robin, least-connections,
                                       #          latency-optimized, weighted
  connectionTimeout: 10000             # Max ms to wait when connecting to a provider (default: 10000)
                                       # Tip: increase to 20000-30000 for cloud providers that
                                       # launch browsers on-demand (cold start can take 10-15s)
  healthCheckInterval: 30000           # How often to check if providers are alive (default: 30000)
  shutdownDrainMs: 30000               # When stopping the gateway, how long to wait for active
                                       # sessions to finish before force-closing (default: 30000)

  cooldown:
    defaultMs: 30000                   # How long to skip a failing provider (default: 30000)
    failureThreshold: 0.5              # Cooldown when failure rate exceeds this (default: 0.5 = 50%)
    minRequestVolume: 3                # Min connection attempts before evaluating (default: 3)

  sessions:
    idleTimeoutMs: 300000              # Close sessions with no activity after this (default: 300000 = 5 min)
    reconnectTimeoutMs: 300000         # How long a disconnected session stays available for reconnection (default: 300000 = 5 min)

  queue:
    maxSize: 50                        # Max requests waiting when all providers are busy (default: 50)
    timeoutMs: 30000                   # How long a request waits in queue before giving up (default: 30000)

providers:
  provider-name:                        # Your name for this provider (any string)
    url: wss://provider.com?token=xxx  # WebSocket URL including any auth params
    headers:                           # Optional. Custom headers sent on the outbound WS upgrade
      Authorization: Bearer ${API_KEY} # Needed for providers that require an Authorization header
    limits:
      maxConcurrent: 10                # Max simultaneous connections (optional, no limit if omitted)
    priority: 1                        # Lower number = tried first (default: 1)
    weight: 1                          # For weighted strategy: higher = more traffic (default: 1)
    profile: my-profile-slug           # Optional. Pin this slot to one profile (see Profiles)
    multiProfile: false                # Only the self-hosted runtime may set this to true
    enabled: true                      # Optional. false keeps the provider configured but never routes to it

# Optional: get notified when things happen
webhooks:
  - url: https://hooks.slack.com/services/xxx    # Where to send notifications
    events: [provider.cooldown, provider.down]    # Which events (omit for all events)

dashboard:
  enabled: true                        # Enable web dashboard at /web (default: true)

logging:
  level: info                          # debug | info | warn | error (default: info)

# One-shot REST endpoints (/v1/screenshot, /v1/content, /v1/scrape)
rest:
  allowedPrivateHosts: []              # Hostnames these endpoints may reach even though they
                                       # point at a private address (default: none)
```

## Providers

### URL

The URL is the WebSocket endpoint of your browser provider. It includes everything the provider needs for authentication - tokens, API keys, session IDs.

```yaml
providers:
  # Cloud provider with token auth
  cloud-provider:
    url: wss://provider.example.com?token=${PROVIDER_TOKEN}

  # Self-hosted Playwright server
  my-playwright:
    url: ws://playwright-host:3000

  # Raw Chrome with remote debugging
  my-chrome:
    url: http://chrome-host:9222              # Auto-discovers WebSocket endpoint

  # Any WebSocket endpoint
  my-custom:
    url: ws://custom-service:8080/browser
```

### Limits

```yaml
limits:
  maxConcurrent: 10    # Max simultaneous connections to this provider
```

When a provider reaches `maxConcurrent`, the gateway skips it and tries the next one. If not set, there is no connection limit.

### Priority

```yaml
priority: 1    # Lower = higher priority. Tried first in priority-chain strategy.
```

Providers with the same priority are tried in config order.

### Weight

```yaml
weight: 3    # For weighted strategy only. Higher = more traffic. Default: 1.
```

Weights only matter when using the `weighted` strategy. A provider with `weight: 3` gets 3x more traffic than one with `weight: 1`. See [Load Balancing](/operating/load-balancing#weighted) for detailed examples.

### Enabled

```yaml
enabled: false    # Keep the provider configured but never route to it. Default: on.
```

A disabled provider is skipped by every strategy, is not health-checked, and a request pinned to it is rejected as if it did not exist. See [Turning A Provider Off](/providers#turning-a-provider-off).

### Custom headers

```yaml
providers:
  cloud-with-bearer:
    url: wss://provider.example.com
    headers:
      Authorization: Bearer ${API_KEY}
      X-Client: browser-gateway
```

Arbitrary key/value headers sent on the outbound WebSocket upgrade to the provider. Needed for providers that require an `Authorization: Bearer` header instead of a URL query token, or that expect any other custom handshake header.

Merge order for outbound headers:

1. Router userinfo (`https://user:pass@host`) resolves to `Authorization: Basic ...`
2. Explicit `headers:` values override any client-supplied header of the same name

Limits: 20 headers max, key up to 80 chars, value up to 4 KB.

### Pin to a profile

```yaml
providers:
  provider-team-acme:
    url: wss://provider.example.com?token=${TOKEN_A}
    profile: team-acme
```

Pins this slot to serve only `?profile=team-acme` connections (plus stateless traffic when no unpinned slot exists). Required for write-back profile use on external CDP providers. See [Profiles](/profiles#provider-isolation) for the full rationale.

### Multi-profile

```yaml
providers:
  runtime:
    url: ws://browserserve:9222/
    multiProfile: true    # Only accepted on the self-hosted runtime
```

`multiProfile: true` tells the gateway this provider can serve multiple profiles concurrently on the same slot. This is only safe on the [self-hosted runtime](/browserserve), where every session gets a fresh isolated Chrome by construction.

Setting `multiProfile: true` on any other provider is rejected two ways:

- **When added over the API**, the gateway probes the upstream first. If it answers but
  is not the self-hosted runtime, `POST /v1/providers` returns HTTP 400 with
  `"multiProfile:true is only valid on browserserve providers"`. If it does not answer
  the probe at all, the request is still refused, with a separate error,
  `"Cannot verify multiProfile:true, the upstream did not answer the probe"`, and the
  probe failure in `details`. Either way nothing is written to `gateway.yml`.
- **When already in `gateway.yml` at startup**, the gateway probes each provider, then
  clears the flag to `false` on any that is not the self-hosted runtime and logs a
  config error naming the provider. The gateway still starts, and that provider runs as
  if the flag had never been set.

Configs loaded from disk with the same flag on a non-runtime provider are logged as an error at boot and the flag is ignored at runtime.

## One-Shot REST Endpoints

`POST /v1/screenshot`, `POST /v1/content` and `POST /v1/scrape` take a `url` and load
it in a browser for you. Because the gateway is the one fetching the page, the `url`
is restricted:

- It must start with `http://` or `https://`. Other schemes, including `file:`, are refused.
- Its host must be a public address. Addresses that only mean something inside your
  own network are refused: `localhost` and `127.0.0.1`, the `10.x`, `172.16-31.x` and
  `192.168.x` ranges, the `169.254.x` range used for cloud metadata services, and the
  `.local` and `.internal` name suffixes.
- Hostnames are looked up, and every address they resolve to is checked the same way.
  A public name that points at a private address is refused too.

A refused request comes back as HTTP 400 with the host named in the message.

To screenshot something on your own network, such as a staging site, list its hostname:

```yaml
rest:
  allowedPrivateHosts:
    - staging.internal
    - 127.0.0.1
```

Matching is on the hostname exactly as written in the request, lowercased. A listed
hostname skips both the literal-address check and the lookup check. The list is empty
by default, so nothing private is reachable until you add it.

## Environment Variable Interpolation

Use `${ENV_VAR}` syntax in any string value. The gateway resolves these at startup.

```yaml
providers:
  production:
    url: wss://service.com?token=${API_TOKEN}
```

Supports defaults with `${VAR:-default}`:

```yaml
gateway:
  port: ${PORT:-9500}
```

Secrets should ALWAYS use env vars. Never put actual tokens in the config file.

## Environment Variables (No Config File)

These environment variables can be set alongside or instead of a config file:

| Variable | Description | Default |
|----------|-------------|---------|
| `BG_TOKEN` | Auth token (if set, all connections require it) | None (no auth) |
| `BG_ENCRYPTION_KEY` | Profile encryption key (auto-generated under `$BG_DATA_DIR/.encryption-key` if unset) | Auto |
| `BG_DATA_DIR` | Where the gateway stores config, profiles, and the encryption key | `/data` (Docker), `~/.browser-gateway` (otherwise) |
| `BG_CONFIG_PATH` | Path to gateway.yml | `$BG_DATA_DIR/gateway.yml` |
| `BG_ALLOWED_ORIGINS` | Cross-origin allowlist (comma-separated) | Same-origin only |
| `BG_ALLOWED_HOSTS` | Extra `Host` header values accepted on `/mcp` when `BG_TOKEN` is unset (comma-separated) | Loopback only |
| `PORT` | Server port (12-factor convention used by Railway, Render, Fly, Heroku) | 9500 |
| `HOST` | Bind interface. Setting it always wins over the default below. | `0.0.0.0` when `BG_TOKEN` is set, `127.0.0.1` when it is not |
| `LOG_LEVEL` | `debug` / `info` / `warn` / `error` (overrides `gateway.yml`) | `info` |
| `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` | Outbound proxy (honored by Node's built-in fetch) | None |
| `TZ` | Timezone for log timestamps | System default |

### Which interface the gateway listens on

An interface is the network address the gateway answers on. `0.0.0.0` means every
address the machine has, so other machines on the network can reach it.
`127.0.0.1` (also called loopback) means only programs on the same machine can.

If `BG_TOKEN` is not set, the `/v1/*` routes have no authentication, so the
gateway binds to `127.0.0.1` and stays private to the machine it runs on. Set
`BG_TOKEN` and it binds to `0.0.0.0` instead. Setting `HOST` yourself always wins,
so `HOST=0.0.0.0` still opens an unauthenticated gateway if that is what you want.

If the gateway used to be reachable from another machine and now is not, set
`BG_TOKEN` (recommended) or set `HOST=0.0.0.0` explicitly.

### .env File

The gateway automatically loads a `.env` file from the current directory. Put secrets here instead of passing them inline:

```bash
# .env
BG_TOKEN=my-secret-token
```

The `.env` file is loaded on startup. Environment variables set externally (e.g., via Docker `-e` flags) take precedence over `.env` values.

## Multiple Providers Example

```yaml
version: 1

providers:
  # Cloud provider - use first
  cloud-primary:
    url: wss://provider.example.com?token=${PRIMARY_TOKEN}
    limits:
      maxConcurrent: 3
    priority: 1

  # Self-hosted servers - overflow
  playwright-1:
    url: ws://playwright-server-1:3000
    limits:
      maxConcurrent: 10
    priority: 2

  playwright-2:
    url: ws://playwright-server-2:3000
    limits:
      maxConcurrent: 10
    priority: 2

  # Second cloud provider - last resort
  cloud-backup:
    url: wss://backup-provider.example.com?key=${BACKUP_KEY}
    limits:
      maxConcurrent: 20
    priority: 3
```

This setup: use the primary cloud provider first (3 concurrent), overflow to self-hosted Playwright servers (20 concurrent across 2 servers), fall back to the backup provider if everything else is full.

## Session Pool

The session pool manages browser connections for the REST API endpoints (`/v1/screenshot`, `/v1/content`, `/v1/scrape`). Instead of opening a new browser connection for every request, the pool keeps a small number of long-lived connections and creates lightweight pages (tabs) within them.

```yaml
pool:
  minSessions: 0          # Minimum browser sessions to keep alive
  maxSessions: 5           # Maximum browser connections from pool
  maxPagesPerSession: 10   # Pages per browser before creating another
  retireAfterPages: 100    # Recycle browser after this many total pages
  retireAfterMs: 3600000   # Recycle after 1 hour max
  idleTimeoutMs: 300000    # Close idle browsers after 5 minutes
```

| Setting | Default | What it does |
|---------|---------|-------------|
| minSessions | 0 | How many browser sessions to keep alive even when idle. 0 means scale to zero, no browser running until the first REST request. Set to 1 to eliminate cold start latency. |
| maxSessions | 5 | Hard cap on total browser connections. 5 sessions with 10 pages each = 50 concurrent REST operations. |
| maxPagesPerSession | 10 | When a browser session has this many active pages, the next request creates a new session. Higher values use less connections but put more load on each browser. |
| retireAfterPages | 100 | After serving this many total pages, the session is marked for retirement. It finishes active pages, then closes. This prevents Chrome memory leaks from accumulating over time. |
| retireAfterMs | 3600000 | Maximum lifetime of a browser session (1 hour). Even if the page count hasn't been reached, long-running sessions are recycled. |
| idleTimeoutMs | 300000 | Close idle sessions (no active pages) after this many milliseconds. Only applies to sessions above minSessions, the pool never closes below the minimum. |

**When to adjust these settings:**

- **High throughput, beefy providers:** Increase `maxPagesPerSession` to 20 and `maxSessions` to 10
- **Memory-constrained providers:** Lower `maxPagesPerSession` to 5, lower `retireAfterPages` to 50
- **Zero idle cost:** Keep `minSessions: 0` (default): browsers only run when requests are active
- **Zero cold start:** Set `minSessions: 1`, one browser stays warm at all times
